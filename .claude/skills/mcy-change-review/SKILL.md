# MCY change review

Use this skill for MCY feature work and handoff. Read the repository's `AGENTS.md`, the user's latest decision, the affected code/docs, and `git status` before choosing a gate. `AGENTS.md` holds runtime and authorization boundaries; source files and current configuration establish what actually exists. Dated analysis is evidence or a proposal, not a newer rule simply because it is detailed. The latest explicit user decision supersedes historical candidates.

For every MCY task, follow the [task lifecycle](../../../docs/quality/TASK_LIFECYCLE.md) and its intake/QC templates: record impact, working baseline, risk and mapped regression before implementation; freeze evidence, complete required independent QC and final/root verification before handoff. R0 can be brief. Existing authorizations and explicit user step boundaries persist; guidance does not enforce runtime or repository permissions.

0. Read [docs/quality/KNOWN_INCIDENTS.md](../../../docs/quality/KNOWN_INCIDENTS.md) first and name the entries that apply in the handoff. **Any change to client code or CSS also follows [mcy-ios-compat](../mcy-ios-compat/SKILL.md)**: the iOS 15.0 baseline is a hard gate, `npm run check:ios15` must be green before any push, APK or AAB, and the real-iPhone check is CHƯA CHẠY unless it was done. A pass on Edge/Chromium never shows old-iPhone behaviour. For Supabase migrations and Edge deploys follow [mcy-supabase-rollout](../mcy-supabase-rollout/SKILL.md).
1. State the observable outcome, authorized scope and affected app surfaces/data/roles. For a plan-only task, produce the plan and update requested guidance; do not silently implement the planned feature.
2. Classify the **highest** risk in the diff as R0–R3 using [review-matrix.md](references/review-matrix.md). Select checks for that risk and the actual behavior changed. Verify commands and provider state before citing them; never report a proposed check as already running.
3. Keep security boundaries in `AGENTS.md` and `supabase/README.md`: no client secret, no self-granted teacher role, no teacher access to learner data by default, no private draft in the learner catalog, no inferred improvement from absent feedback. For database/API changes, inspect effective schema and table grants separately from RLS policies; include `TRUNCATE` and inherited `PUBLIC` privileges because RLS does not guard every table operation. Verify the intended server role actually has required private-schema privileges instead of assuming possession of a service-role key grants them. For `SECURITY DEFINER` RPCs, check execute grants (exclude `anon`/`PUBLIC` unless justified), a pinned safe `search_path`, qualified objects, authenticated identity/ownership checks, and negative actor tests. Use live privilege/catalog evidence plus actor-based negative API tests for ownership, consent, roles and media. A policy listing or advisor result alone is not an authorization test.
4. Run the applicable checks after the final edit. Record command, exit status, environment and commit/revision where possible as **PASS**, **FAIL** or **CHƯA CHẠY**. A build or runtime fixture pass does not prove learner behavior or RLS. If a required gate fails, fix the cause or stop that release scope; do not weaken tests, policies, checker or lock to get green.
5. Review the guidance impact in the same change (and keep `AGENTS.md` under its size limit: when it grows past ~26 KB, compact it per hard gate 6 by moving dated status to `docs/status/`, never by dropping a durable rule): update `AGENTS.md`, brand/design/schema references and this skill only when a durable decision or workflow changed; remove or label superseded rules. Do not freeze provider prices, quotas, external account state or unvalidated English copy in a skill. Check current authoritative sources at execution.
6. Hand off the behavior, tests, untested cases, residual risks and rollback/disable path. Skills are instructions, not a security boundary. A release needs enforceable CI and repository/deploy permissions appropriate to the risk; never claim zero risk.

For consent changes, keep required terms/privacy acceptance version-aware: reuse a current grant across sign-ins, and request it again only when the current version is absent, revoked, or changed. Keep optional purposes independent and editable. Enforce consent at the authenticated server write boundary as well as in the interface; verify unauthenticated, stale-version and revoked-consent calls cannot write. Consent identifiers name the reviewed copy and must not be represented as legal approval.

For teacher access, email verification alone does not grant a teacher role. Keep enrollment invite-only until an owner-authorized, audited server boundary exists, and test that learners and teachers cannot self-elevate or reach learner records. A teacher-facing notice or application screen is not evidence that invitation, activation, draft upload, review or publishing workflows exist.

For Supabase migrations, use `supabase migration new <name>` when the local CLI is available. Verify the recorded remote migration version after application. If an authorized staging migration connector is the only available path, record the exact version it creates in the matching local migration filename and document that fallback. Do not run `supabase db push` while local filenames and remote migration versions disagree; reconcile that history as a separately reviewed change first.

For learner data changes, trace the serialized client payload all the way through the exposed RPC to the stored rows. Keep stored region codes locale-neutral and map application naming to the exact SQL JSON keys explicitly. Preserve existing user preferences and observations when changing defaults or taxonomies. For a `SECURITY DEFINER` wrapper that delegates to a private helper, verify both live function owners and effective EXECUTE privileges after migration; test the authenticated data path and denied anonymous/direct-table paths with disposable staging evidence, and report missing actors as CHƯA CHẠY.

For learner UI changes, inspect the current E2E coverage in `tests/learner-ux.spec.ts` and the Playwright test match/config before deciding which path is covered. The English locale is still an internal partial preview; its main-loop test now also exercises Journey sample and comparison states, but does not establish full English support: consent, account, support and knowledge screens remain Vietnamese. A simulator/browser pass does not establish physical Android/iOS behavior.

Read [review-matrix.md](references/review-matrix.md) when selecting or auditing gates. For visual/copy/interaction work, also use [mcy-brand-ux](../mcy-brand-ux/SKILL.md). Use specialized provider/SDK skills only when the task actually involves them and they are available; avoid skills for other repositories.


## Release evidence workflow - 2026-10-04

For environment/release planning also read docs/release/RELEASE_RUNBOOK.md and the owner packet. Bind the exact commit, full migration hashes, built files, config expectations and tests to one manifest. Preserve the three pending-migration/actor gates; a manual timestamp comparison or local checker cannot clear them. Rehearse clean schema and production-schema upgrade with fictional fixtures, test grants/RLS/Storage/RPC/views and revoked roles/old tokens, and retain older-client compatibility. Only the exact owner-approved target/artifact may enter a separately verified protected release path. The local checker has no credentials or deploy capability.

For shipping to web, the test phone and Google Play, follow [mcy-release-sync](../mcy-release-sync/SKILL.md) and `docs/release/CROSS_PLATFORM_RELEASE.md`: one committed HEAD for every platform, strictly increasing `versionCode`, a ledger row per batch.
