## Live ACL snapshot

- All 46 `public` tables have RLS enabled.
- Before the asset-metadata migrations, the five earlier staging ACL hardening migrations left 30/46 tables granting `TRUNCATE` to both `anon` and `authenticated`, with 30 `anon` INSERT and 31 `authenticated` INSERT grants. After `20260930064345` and `20260930065400`, the live count is 28/46 for `anon` and `authenticated` `TRUNCATE`, 28 `anon` INSERT, and 29 `authenticated` INSERT (the remaining extra authenticated INSERT is `profiles`).
- The 28 remaining client-`TRUNCATE` tables split into 18 with no RLS policy and 10 with read policies only. No table in that set currently has a client write policy. RLS therefore denies ordinary row access on policyless tables, but it does not neutralize `TRUNCATE`; REST actor tests and effective grants are separate evidence.
- Seven learner/session-history tables have write policies but no effective client table privileges. `checkins` and `checkin_observations` give authenticated users SELECT only; `plan_items` is now also SELECT-only. `profiles` is the only remaining app table with client INSERT/UPDATE access, constrained to its owner.
- There are currently no public sequences. Existing public functions have no effective `PUBLIC`/`anon` EXECUTE grants in the live ACL snapshot; the five learner functions above are callable by `authenticated`, while AI control functions are callable by `service_role` only.
- Migrations `20260930064345` and `20260930065400` removed effective `anon` and `authenticated` access to `asset_rights` and `asset_components` while leaving their `service_role` grants unchanged; live catalog checks show RLS enabled, zero policies, and zero rows. The staging anonymous PostgREST regression test checks SELECT/INSERT/UPDATE/DELETE denial for both tables without supplying or changing row data. `asset_components` has no current app/function references; its FK definitions remain intact.
- Default ACL rows for both `postgres` and `supabase_admin` still grant broad future public table and sequence privileges to client/server roles. Public function defaults grant EXECUTE to `anon`, `authenticated` and `service_role`; PostgreSQL's default PUBLIC function EXECUTE behavior also requires explicit consideration. The live default ACL includes table privileges beyond CRUD (including `TRUNCATE`, `REFERENCES`, `TRIGGER`, and `MAINTAIN`).
- Staging currently has zero Storage buckets and zero objects. The organization is on the Free plan. No storage bucket, upload, or paid upgrade was created.

## Proposed permission target

1. Preserve the exact live learner contracts above and all existing function bodies/owners/search paths. Add explicit grants in the migration that creates each future Data API object, rather than relying on inherited defaults.
2. Keep the 20 policyless tables out of the client Data API until a real consumer, row policy, and actor contract are implemented. Retain only the reviewed SELECT grants for intentionally public, published-content read surfaces; never grant client writes on draft, publication, media-rights, audit, or workflow tables.
3. **Completed narrowly on 2026-10-01:** after owner approval and compatibility review, revoke client privileges on the 18 policyless tables and retain SELECT only on the 10 SELECT-policy tables identified below. This did not alter any other table, function, service-role permission, policy, or default ACL. Do not expand this migration's scope without a new reviewed proposal and explicit owner approval.
4. For `postgres`-created future objects, prepare an explicit default-privilege migration that removes automatic grants for `anon`, `authenticated`, and `service_role` from tables/sequences/functions and removes default `PUBLIC` function EXECUTE; then explicitly grant each required object. Recheck sequence/function ACLs and migration ownership after applying.
5. Do not alter `supabase_admin` default privileges in the same step until the Supabase-supported ownership/control path is confirmed. Recheck the platform's scheduled rollout and effective ACL after it rather than assuming internal defaults can safely be changed by an app migration.
6. Role-verified authenticated actor tests using distinct disposable learner A/B, teacher, reviewer and owner actors remain required for their respective APIs; verify each fixture's server-granted role rather than trusting its label. Current `test:teacher-actors` cannot run because those tokens are absent. Keep invitation, private uploads, AI inference and production release disabled until their separate gates pass.

No plan upgrade or external scanning service has been authorized. See [Storage file limits](https://supabase.com/docs/guides/storage/uploads/file-limits) and [Storage pricing/quotas](https://supabase.com/docs/guides/storage/pricing).
