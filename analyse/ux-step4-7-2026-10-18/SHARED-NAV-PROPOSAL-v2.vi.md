# 4.7 shared app navigation: superseding implementation proposal

Status: **design for independent QC and root release only**. No 4.7 app candidate or source/test edit has been made. This supersedes the measured-override design in `IMPLEMENTATION-PROPOSAL.vi.md`; that design is NO-GO because it would render a footer taller than the configured `FlowScreen.footerHeight: 68`.

## Evidence and rule

Read-only baseline v3 completed six captures with process exit 0, no nonlocal request, and unchanged accepted 4.6 pins. At web 320×568, normal navigation labels fit the footer y500–568; the 28px screenshot visibly clips labels. The rapid snapshot's 28px `Range` rectangle was stale before paint, so it is not an acceptance measurement. Independent settled 4.6 control measured label bottom 612 against footer bottom 568. Welcome at 320, short landscape, and desktop has no evidenced crop or hierarchy defect; RegionEditor last note is a separate historical P3. These do not justify unrelated redesign.

`AGENTS.md:320` requires: “Set `footerHeight` to the full app-footer height. `FlowScreen.footer` is an overlay, not reserved layout space; screens using it must add their own bottom content padding”. Keeping `footerHeight: 68` while growing its route-owned footer violates that requirement. `AGENTS.md:319` permits app-owned fixed chrome as a sibling of `MobileScroll` for layered shells. The proposed navigation is one shared app-level element in `FlowStack`'s supported `children` slot, not a route-owned `FlowScreen.footer` moved to evade its contract. Home, Journey, Discover, and Profile no longer declare a route footer at all. Their `FlowStack` footer variable is correctly 0; the app reserves its own shared navigation height in its pages.

## Exact candidate change, after GO only

Source diff from frozen accepted 4.6 is limited to candidate `src/Prototype.tsx` and `src/prototype.css`; add `tests/ux-responsive.spec.ts` and selector-only updates in candidate existing tests listed below. No edit to `src/mobile/**`, `src/styles.css`, `mobile-runtime.lock.json`, root checkout, route handlers, Auth/session/consent, backend, content, media, or build controls. The candidate is a fresh copy of accepted 4.6 inputs with its own manifest and hashes.

In `src/Prototype.tsx`, remove only `footer: () => <BottomNav />` and `footerHeight: 68` from four `ROUTES` entries (home, journey, discover, profile). Keep their ids, headers, render callbacks, and navigation actions unchanged. Add `<SharedBottomNavigation />` once as a `FlowStack` child beside `AuthSessionRouter`, `FlowRouteFocusManager`, and `PracticeCapabilityObserver`. It reads `useFlow().current.id`, renders a `<footer className="mcy-app-navigation" data-testid="mcy-app-navigation"><BottomNav /></footer>` only for those four exact route ids, and remains outside `.flow-scenes` so it never becomes retained/inert route content. `BottomNav` keeps four buttons, current-page state, labels, icons, and existing `flow.replace(ROUTES[item.id])` action. No new router or route transition is introduced.

The shared footer calls `useKeyboardInsets().bottomInset` for its CSS `bottom` and `useKeyboardDismissDrag()` for the same drag-dismiss affordance currently attached to `FlowScreen.footer` (direct import from `./mobile/Keyboard` if not exported by the barrel). The closed iPhone bottom inset clears the 34px home indicator; closed Pixel uses 0 because its viewport already excludes Android navigation; an open keyboard uses the hook's inset without adding keyboard height to `MobileScroll` padding. Footer z-index and bottom transition match existing fixed chrome; transition disables while `.flow-stack[data-keyboard-dragging=true]`. Other route-owned footers retain the unchanged protected FlowStack implementation.

The new navigation has `min-height: 68px` at ordinary type, intrinsic block size when text wraps, four equal visible tabs, `overflow-wrap: anywhere` for English single words, and inner space for the full 3px outline plus 3px offset on all four controls. It never scrolls horizontally, hides a destination, or shrinks user-requested text. A `ResizeObserver` on the intrinsic footer publishes `Math.ceil(borderBoxSize.blockSize)` (fallback `offsetHeight`) as **layout CSS pixels**, not transformed `getBoundingClientRect().height`, to `--mcy-app-nav-height` on its nearest `.flow-stack`. `useLayoutEffect` publishes the initial measurement before paint; observer updates only when height changes. The footer's size does not depend on this variable, preventing an observer sizing loop. A local active/disposed guard plus `disconnect()` and `removeProperty()` on route exit/unmount/StrictMode cleanup prevents late callbacks or stale reservation. On nav-to-nav route changes the single layer stays mounted; on nav-to-non-nav it disappears and clears the variable; on back it measures afresh. No write to protected `--flow-footer-height`, protected attributes, route objects, or screen keys.

In `src/prototype.css`, style `.mcy-app-navigation` as app-owned absolute bottom chrome. Only while it exists, target the **current** `.flow-screen[data-flow-current="true"]`. The generic active `.mcy-page` bottom padding is `calc(var(--mcy-app-nav-height, 68px) + var(--mobile-safe-area-height) + 28px)`; the Profile `.mcy-account-home` uses its existing extra 36px instead of 28px. Active `.mobile-scroll` focus `scroll-padding-bottom` is `calc(var(--mcy-app-nav-height, 68px) + var(--mobile-safe-area-height) + 24px)`, including `.mcy-profile-scroll > .mobile-scroll`. The nav is anchored to `bottomInset`; `MobileScroll` already shrinks by keyboard height. The safe-area term therefore represents only the remaining gap between scroll bottom and footer bottom: iPhone closed 34px, web Pixel closed 0, open keyboard 0, native Android closed its reserved inset. Never add keyboard height to page padding or scroll padding. Apply no nav reservation to retained/inert screens or non-nav routes. Existing route-owned footer CSS and `FlowStack` geometry stay untouched. A scoped focus-visible rule supplies the existing 3px+3px ring to the new shared footer. Prefer `:has(> .mcy-app-navigation)` to scope CSS by real current DOM presence; the observer variable is removed on exit even if the selector already deactivates.

## Impact and selector inventory

This is app-wide shared navigation across four route consumers and affects footer accessibility/focus, keyboard drag, safe-area, content-end clearance, and route transitions. It is not a Profile-only styling fix. Proposed tier **R1 pending independent QC and root confirmation**, because the implementation uses the documented app-owned layered-chrome pattern and changes no protected runtime contract. If review finds that this pattern still changes a protected contract, stop and submit a separately scoped R3 patch/approval; do not silently edit FlowStack or its lock.

Existing tests that select the four-tab navigation through `.flow-fixed-footer` must instead select the real app-owned `data-testid="mcy-app-navigation"` (or `.mcy-app-navigation`) in the **new candidate only**, with assertions, timeouts, and actions unchanged: `ux-profile.spec.ts` entry, focus geometry, device inset, and Home return; `practice-flow.spec.ts` three nav opens; `learner-write-review.spec.ts` three Profile opens; `learner-ux.spec.ts` English Main navigation selectors; and `learner-device-acceptance.spec.ts` nav helper. `ux-home.spec.ts` already selects `.mcy-bottom-nav` and needs no migration. `mobile-runtime.spec.ts` uses a separate runtime fixture's `flow-fixed-footer` and must remain unchanged. References to Check-in, Welcome, Consent, or Reflection route-owned footer in `learner-ux`, `ux-checkin-layout`, `ux-energy-time`, `ux-reflection`, and runtime fixture tests remain unchanged. The old Profile 28px focused-bounds test keeps its same assertion, now reads the real shared app footer geometry. Candidate test diff must show selector-only migrations and no weakened expectation.
