# 4.7 shared navigation test correction

This narrow addendum binds [the frozen v2 design](SHARED-NAV-PROPOSAL-v2.vi.md) and supersedes only its case 4 description. It does not approve app/browser execution or change any source.

The four shared-nav routes contain no stable `KeyboardInput`. A Profile → Edit Profile transition has a real `KeyboardInput` (`Tên hiển thị`), but the shared navigation correctly disappears on that detail route. Therefore an app browser case must **not** claim to drag the shared nav while a keyboard is open. The direct `useKeyboardDismissDrag()` attachment on the shared `<footer>` is checked in source review, and the unchanged `mobile-runtime.spec.ts` `keyboard and its attached footer dismiss on the same transition` remains a runtime-hook control, not proof of an open-keyboard shared nav state. No artificial keyboard injection is proposed.

Revised new case 4 exact title: `BottomNav Profile to edit input and back clears ownership and restores measured clearance`. From Profile, record the current screen's final content geometry, scroll position, footer top, and `--mcy-app-nav-height`; open `Thông tin cá nhân`, assert the shared nav count is 0, the app variable is removed, and the detail's input can focus with a keyboard without inherited nav padding; go back through the existing button, wait for keyboard dismissal and route settlement, assert one current non-inert Profile screen, one newly measured nav, and final-content/focus clearance. Compare the returned Profile scroll position and last content geometry to its pre-transition settled state within a small browser-rounding tolerance; route changes may intentionally change focus but may not leave content below the footer or produce a persistent jump. Repeat nav → course detail → back without an input to prove shared layer cleanup across another retained route. This supplements, rather than changes, the exact old Profile assertions/timeouts.

The iPhone/Pixel new cases still test keyboard inset on their existing route-owned input/footer controls and verify shared-nav safe area when keyboard is closed. They must not claim a reachable shared-nav open-keyboard state. The source review verifies that shared nav uses `useKeyboardInsets().bottomInset`, not `keyboardHeight`, and that the `MobileScroll` viewport's existing keyboard shrink is never added again to app page/scroll padding.
